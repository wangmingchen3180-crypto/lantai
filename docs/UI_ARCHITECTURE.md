# UI 可变性：现在改一次 UI 要花多少钱

写这份文档的起因是一个真实担心：**现在的界面是权宜之计，以后要改、要做皮肤，但不想因此把项目做成屎山。**

所以这里不谈「应该模块化」这种正确但没用的话，只回答一个问题：今天想改界面的某一层，具体要动多少地方。数字全部来自 2026-08-14 对 `Sources/CodexPulse/` 的实测统计，不是估计。

## 结论先放

改 UI 不是一件事，是四件成本差一个数量级的事：

| 想改什么 | 现在的成本 | 卡在哪 |
| --- | --- | --- |
| 换颜色（换一套色板） | 便宜。改 12 个函数 | 无。142 个调用点全部走这 12 个函数 |
| 运行时切换皮肤（不重启就变色） | 中等。要处理 65 处 | `CALayer.CGColor` 是快照，不跟随动态颜色 |
| 换密度（圆角、间距、字号） | 中等偏贵。约 160 个散落数字 | 这些数字直接写在布局代码里，没有集中的地方 |
| 换布局和交互 | 贵。必须动那个 1712 行的类 | `CPWorkbenchCardController` 一个类同时管窗口、布局、数据、交互 |

**好消息**：真正难挽回的那部分（数据层被 UI 污染）没有发生。`CPModels` / `CPTodoStore` / `CPAgentSources` / `CPStatusEngine` / `CPStateCache` 不 import 任何控制器，依赖方向是干净的。这意味着**换 UI 不需要重写核心**，最坏情况是重写视图层，而视图层本来就是要换的东西。

**坏消息**：现在没有任何独立的东西负责「决定界面长什么样」。这个职责散落在控制器里，和数据获取、交互响应搅在一起。所以换布局的成本不是「改布局代码」，而是「在 1712 行里把布局代码从别的东西里挑出来」。

## 逐层看

### 一、颜色：已经是对的

12 个调色板函数集中在 `CPStatusEngine.m` 顶部（`CPAccent` / `CPBg` / `CPSurface` / `CPBorder` / `CPFg` / `CPFg2` / `CPMuted` / `CPBlue` / `CPOrange` / `CPRed` / `CPGreen` / `CPHairline`，底座是 `CPDyn`），全项目 142 处调用都走它们。

换一套配色 = 改这 12 个函数的返回值。这一层不欠债。

例外只有 7 处直接写了 `NSColor`，绕过了调色板：

- `CPWorkbenchController.m:259`、`CPHUDController.m:436`、`CPDockController.m:83`/`:102`/`:150` —— 阴影色
- `CPWorkbenchController.m:509` —— 待办输入框底（黑 22%）
- `CPHUDController.m:16` —— HUD 某处白 12%

阴影色其实应该是 token（`--shadow`），顺手收进调色板即可，工作量分钟级。

### 二、运行时换肤：卡在 65 处 CGColor

`CPDyn` 返回的是动态颜色，系统外观变化时会自动重算。但代码里有 **65 处**把它拍成了 `.CGColor` 赋给 `CALayer`：

```
CPWorkbenchController.m  19 处
CPControls.m             18 处
CPHUDController.m        14 处
CPDockController.m       14 处
```

`CGColor` 是快照，不会跟随。所以「设置里点一下就换肤」会出现一半变了一半没变——描边、状态灯、hover 底色留在旧色上。

两条解法：

1. **重启生效**（首版建议）。切换皮肤后提示重新打开窗口，或直接重建三个窗口。零重构成本。
2. **注册重刷**。所有拍 `CGColor` 的地方登记到一张表，换肤时统一重赋。一次性把 65 处收拢，之后免疫。

首版走 1。真做用户可切换皮肤时再上 2，且**上 2 的同时必须加一条自测**：换肤后随机抽查若干 layer 的实际颜色，否则这类「一半没变」的 bug 靠肉眼发现不了。

### 三、密度：约 160 个散落数字

这是目前最实在的一笔债。已经命名成常量的有 36 个，但都是窗口/卡片级的大尺寸（`CPCardWidth 520`、`CPCardHeight 360`、`CPHUDContentWidth 400`、`CPOrbSize 48` 等）。真正决定「看起来松还是紧」的小数字全是字面量：

| 类别 | 数量 | 分布 |
| --- | --- | --- |
| 约束里直接写的数字 | 116 | 工作台 81 · HUD 26 · Dock 7 · 控件 2 |
| `cornerRadius = 数字` | 23 | 工作台 13 · HUD 6 · Dock 2 · 控件 2 |
| 字号直接写数字 | 19 | 工作台 8 · HUD 7 · Dock 4 |

后果：想把界面整体调紧一档，或者做一套「大字版」，得在三个文件里挨个找数字，且没法验证有没有漏。

**这是唯一现在就值得花的钱。** 抽一张 token 表：

```objc
// 圆角：卡片 10 / 行 8 / 胶囊 8 / 输入 8（与 Resources/mobile/assets/app.css 同源）
CGFloat CPRadius(CPRadiusRole role);
// 间距：4 / 8 / 12 / 14 / 20 阶梯，不允许出现阶梯外的值
CGFloat CPSpace(CPSpaceStep step);
// 字号：与 NSFont 权重成对，一处定义
NSFont *CPFont(CPTextRole role);
```

理由不是「好看」，而是：不管未来是换皮、换布局，还是做手机端对齐，都要用到这张表；而且这活是机械替换，风险低，可以分文件慢慢做，不需要一次做完。反过来，如果一直不做，每加一个新界面就多几十个字面量，债是线性增长的。

顺带解决一个已经存在的一致性问题：手机端 `Resources/mobile/assets/app.css` 已经把圆角、间距抄成了 CSS 变量。现在两边靠「改 Mac 前先改这里」的注释维持同源，靠纪律。Mac 端有了 token 表之后，可以从它生成 CSS 变量，同源变成机制。

### 四、布局和交互：真正贵的地方

`CPWorkbenchCardController` 1712 行，头文件暴露 52 个属性，同时承担四个职责：

1. 持有窗口和面板（`window` / `shadowCarrier` / `card`）
2. 构建布局（三列、头部、待办栏，176 处约束）
3. 拿数据并渲染（`renderAgents:` / `renderTodos` / 直接持有 `todoStore`）
4. 响应交互（`taskClicked:` / `agentClicked:` / `handleEscape` / hover 恢复 / 拖拽）

换布局必须动它。而动它的时候，你会发现布局代码和数据渲染、交互响应交织在一起，改动面无法收窄——**这就是「屎山」的实际手感：不是代码丑，是改一处必须理解全部。**

那 52 个暴露的属性大半是给自测断言用的。这不是坏事（自测确实值），但它让「改结构」的代价变高：换布局要同时改自测的取值路径。

## 那到底要不要现在重构

**不要。** 理由：

现在拆 `CPWorkbenchCardController`，是在不知道未来界面长什么样的情况下凭想象划边界。划错了就是白拆一遍，还得再拆一次——那才是真正的「屎上雕花」。正确的时机是**你真的开始改布局的那一次**，那时才知道哪条缝该在哪。

现在要做的只有一件事，而且几乎不花钱：**加一条防线，别让债继续长。**

### 三条规矩（从四象限这一版开始执行）

1. **新界面不进 `CPWorkbenchController.m`。** 新的 UI 各自成文件，形式是「一个 View 负责长什么样 + 一个薄对象负责数据和交互」。这不叫架构，就是不往那个 1712 行的文件里再加东西。
2. **新界面不许出现新的字面量。** 圆角、间距、字号一律走 token（token 表还没有就先在自己文件顶部定命名常量，之后统一收进去）。旧文件不要求同步整改。
3. **新界面的自测断言只钉行为，不钉像素。** 断言「点第二格之后第二格是展开态」「新增后列表多一条」这类；不断言「这一格宽 250」。行为断言在换皮换布局后仍然成立，像素断言会在你改设计的那天变成 200 条要返工的负债。

第 3 条最重要，也最容易被忽略。现在自测里有 124 处几何断言，好消息是它们大多引用命名常量（改 `CPCardWidth` 断言会跟着走），坏消息是仍有写死数字的，且有几个测试名本身写死了尺寸（例如 `card-520x402`）——尺寸一改，名字就开始说谎。

## 皮肤 ≠ 换 UI，别用一个机制做两件事

原始担心里有一句是「不同皮肤可能交互逻辑也会发生变化」。这一句要拆开，因为它藏着一个陷阱：

- **皮肤**：同一套交互，换颜色（可能再换密度）。用户预期是「还是那个软件，换了身衣服」。
- **换 UI**：交互本身变了。用户预期是「这是另一种用法」。

如果用皮肤机制去承载交互变化，皮肤配置就会长成一个能改一切的万能开关——每加一种皮肤都要往里塞新分支，每个分支都要单独测。**这是屎山最典型的长法之一：一个本来简单的机制被赋予了无限可能性。**

所以定死边界：

- 皮肤只覆盖颜色，首版最多再加密度。**不覆盖交互、不覆盖布局结构。**（与 `DESIGN.md` 已定的「涟漪几何、环数、速度不随皮肤变」一致）
- 真要有两种交互形态（例如「极简模式 / 完整模式」），那是两个视图实现，共用同一个数据层，各自有自己的文件和自己的自测。**不是两套皮肤配置。**
- 判断标准很简单：**如果切换后自测断言需要换一套，那它就不是皮肤。**

## 四象限：第一个按新规矩做的界面

待办四象限的空间冲突已经有解，方案来自用户：**四格缩略 + 点选放大。** 四格常态各占一小格（只显示象限名、条数、最多一两条标题），点中的那一格放大成可读可录入的完整列表，其余三格让位收成窄条。

这个方案好在三点：

1. **解决了空间问题。** 现在待办展开态给列表的是 520×158，硬摊 2×2 每格只剩两行高，装不下。缩略 + 放大后，任何时刻只有一格需要完整高度。
2. **手机端天然复用。** 窄屏摊不开 2×2，但「四格概览 → 点开一格」在手机上正是标准交互，不需要为手机另设计一套。
3. **它是一块干净的试验田。** 待办四象限不依赖工作台那三列的任何东西，可以完全按上面三条规矩新建文件写，不碰 1712 行。写完就知道这套规矩是否真的可执行。

因此四象限的实施顺序是：先按新规矩把界面写出来（独立文件、走 token、只钉行为断言），再回头补数据层字段。不是反过来。

配套字段（`CPTodoStore` v1→v2）在 [BACKLOG.md](BACKLOG.md) 待办一节，要点是象限存 `urgent` / `important` 两个布尔而不是一个枚举——拖到另一格只是改一个布尔，且以后想单独按重要性筛选不必再迁移一次表。

## 复查用的数字

以后想知道债有没有变大，重跑这几条即可（数字是 2026-08-14 的基线）：

```bash
cd "$(git rev-parse --show-toplevel)"
sum() { awk -F: '{s+=$2} END {print s+0}'; }

# 散落的密度字面量：基线 约束 116 · 圆角 23 · 字号 19
rg -c "constraintEqualToConstant:[0-9]|constant:[0-9-]" Sources/CodexPulse/*.m | sum
rg -c "cornerRadius = [0-9]" Sources/CodexPulse/*.m | sum
rg -c "systemFontOfSize:[0-9]|FontOfSize:[0-9]" Sources/CodexPulse/*.m | sum

# 换肤要重刷的 CGColor 快照：基线 65
rg -c "\.CGColor" Sources/CodexPulse/*.m | sum

# 绕过调色板直写颜色：基线 7（应趋近 0）
rg -n "colorWithSRGBRed|colorWithWhite" Sources/CodexPulse/*.m | rg -v CPStatusEngine

# god object 体量：基线 1712 行 / 52 个暴露属性，两个都不许涨
wc -l Sources/CodexPulse/CPWorkbenchController.m
rg -c "^@property" Sources/CodexPulse/CPWorkbenchController.h
```

第 3 条和第 5 条是硬线：**绕过调色板的数量不许涨，`CPWorkbenchController.m` 的行数不许涨。** 其余允许缓慢改善。
